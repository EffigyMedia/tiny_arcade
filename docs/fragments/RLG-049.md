### RLG-049 — A wrong address should open the arcade, not a 404

- Description: The owner reported that people he shared the arcade with were getting 404s. **The
  site is not broken.** Measured on 2026-08-24, every asset the launcher needs returns 200, the
  service worker registers, and all eighteen cabinets are reachable. The 404s come from the address
  people arrive at, and there are four of them:

  | address | result |
  |---|---|
  | `/tiny_arcade/` and `/tiny_arcade` | 200 |
  | `/Tiny_Arcade/` | **404** - Pages paths are case-sensitive, and the project folder on the owner's disk is capitalized |
  | `/tiny-arcade/` | **404** - a hyphen is the natural way to write a two-word name |
  | the bare `effigymedia.github.io/` | **404** - no user-level site exists |
  | `/tiny_arcade/games/highway.html` | **404** - the pre-shelf layout |

- **The last row is the one that is nobody's typing mistake.** The cabinets moved into
  `games/<shelf>/` folders, so **every link shared before that move is dead**, and so is every
  bookmark saved from one. That is a link the owner sent, working when sent and broken now.
- Implementation, and what it can and cannot reach:
  - **`404.html`** at the repository root. GitHub Pages serves it for any missing path under the
    site, so old cabinet links, typos in a sub-path and stale bookmarks all land in the launcher
    instead of on a host error page.
  - **The way home is computed, not written down.** This page is served for any missing path, so a
    relative URL inside it resolves against the path that was REQUESTED rather than against the
    file. The rule used instead: on a `github.io` host the site root is the first path segment;
    anywhere else it is `/`. **It names no repository**, so it survives a rename and it is already
    correct if the arcade ever moves to a host that serves at the root ([[RLG-043]]).
  - It redirects with `location.replace`, not `assign`, so the dead address does not enter history
    and Back does not walk into it again.
  - **`.nojekyll`**, so Pages never runs the site through Jekyll. Nothing needs it today; it costs
    one empty file and removes a class of silent exclusion.
- **What this does NOT fix, and it is the more likely of the two:** a wrong address that is not
  under `/tiny_arcade/` at all - the capitalized one, the hyphenated one, and the bare domain. Those
  never reach this repository. Only a user-level site at `EffigyMedia.github.io` can catch them, and
  that is a second repository and the owner's decision.
- Verified: the redirect rule was proved against seven address shapes, including two hosting
  layouts, before it shipped. The build gate passes with `404.html` on the whitelist and `.nojekyll`
  deliberately off it - the staging area refuses dotfiles, so listing it would fail the build it
  exists to protect.
- **RULED 2026-08-24T22:33:03-04:00** — AMENDED 2026-08-24 - THE OWNER SAYS THE FRIENDS HAD THE CORRECT URL, WHICH THE FIX ABOVE DOES NOT EXPLAIN. Recording what was ruled OUT, because the next person to look at this should not repeat it. **The site was never down.** Every Pages build in the recorded history succeeded; the entries that read `errored` with a duration of 0 are queued builds that GitHub cancelled when another push landed seconds later, and each is followed within the minute by a build that succeeded. **The catalogue never pointed at a missing file**, either: the four most recently deployed commits were checked directly, and all eighteen cabinets named in `games.js` were present in the tree at each one. So the chronic 404 this project has a history of - a launcher advertising machines that were never uploaded - was not happening. **WHAT REMAINS, AND THE FIRST IS CHECKABLE AGAINST THE OWNER'S MEMORY.** The repository was created at 11:52 UTC on 2026-08-19 and the first recorded Pages build is 22:36 UTC the same day. **For about ten hours the address existed and the site did not**, so anybody given the link in that window got GitHub's own 404 page - and a person who tries a link once and gets an error does not usually try it again a day later. The second: they followed a link to a CABINET rather than to the arcade, which was dead until the fix above and is now a redirect. Neither is proved. **The distinction that would settle it is what the friend actually saw** - GitHub's 404 page, or the arcade loading and then a machine failing to open.
